**Structure:**

1. **Frontmatter:**
   - name: ptf-orchestrator
   - description: Coordinates wave-by-wave task execution with parallel dispatch
   - tools: Read, Write, Bash, Glob, Grep, Task

2. **Role section:**
   - Wave-by-wave execution coordination
   - Parallel task dispatch within waves
   - Result collection and checkpoint triggering
   - Failure handling and progression decisions

3. **Philosophy section:**
   - Waves are synchronization points
   - Tasks within a wave are independent
   - Checkpoints happen at wave boundaries (never skip)
   - State manager handles persistence (orchestrator delegates)

4. **Execution flow with operations:**

   operation: execute_wave
   - Input: wave number, tasks list
   - Load max_parallel from config
   - Batch tasks into chunks of max_parallel
   - For each batch:
     - Dispatch tasks via Task tool to ptf-executor
     - Wait for batch completion
     - Collect results
   - Return aggregated results

   operation: dispatch_task
   - Input: task definition
   - Prepare fresh context prompt with:
     - Task id, name, description
     - Input file contents (read and include)
     - Output expectations
     - Verification criteria
     - Execution mode (ralph/single-shot)
     - Max iterations
   - Spawn via Task tool with subagent_type: ptf-executor
   - Parse executor return (VERIFICATION PASSED / BLOCKED)

   operation: handle_wave_results
   - Input: wave number, task results array
   - Count: succeeded, failed, blocked
   - Determine wave status:
     - All succeeded -> completed
     - Some failed -> partial
     - All failed -> failed
   - Invoke state manager for checkpoint
   - Decide continuation:
     - Wave complete + more waves -> continue
     - Wave partial + can_proceed -> continue with warnings
     - Wave failed or blocked -> pause for intervention

   operation: execute_plan
   - Input: start_wave (default: next pending)
   - Loop through waves from graph.yaml:
     - Validate wave dependencies satisfied
     - Execute wave
     - Handle results
     - Continue or pause based on policy
   - Complete when all waves done or blocked

5. **Parallel dispatch section:**
   - Task batching for max_parallel limit
   - Concurrent Task tool invocation pattern
   - Result aggregation from multiple executors

6. **State integration section:**
   - Pre-wave: invoke state_manager.start_wave
   - Post-task: invoke state_manager.task_completed/failed
   - Post-wave: invoke state_manager.checkpoint_wave
   - Event logging happens via state manager (not directly)

7. **Structured returns:**
   - WAVE COMPLETE: Wave N succeeded/partial with summary
   - PLAN COMPLETE: All waves executed successfully
   - EXECUTION PAUSED: Waiting for intervention (failures)
   - EXECUTION BLOCKED: Cannot proceed (dependencies not met)

Follow established agent patterns from ptf-state-manager.md.

**File: .orchestrator/config-example.yaml**

This file demonstrates the configuration options for execution:

```yaml
# PTF Configuration Example
# Copy to .orchestrator/config.yaml and customize

domain: software-development

execution:
  # Execution mode for tasks
  # ralph: Repeat task until verification passes (default)
  # single-shot: Run task once, fail if verification fails
  default_mode: ralph

  # Maximum concurrent tasks per wave
  # Tasks are batched if wave has more than this many
  max_parallel_tasks: 5

  ralph:
    # Default max iterations for Ralph-style execution
    max_iterations: 10

    # Phrase that signals task completion
    completion_promise: "VERIFICATION PASSED"

    # Phrase prefix that signals task is blocked
    blocked_phrase: "BLOCKED:"

    # Delay between iterations (seconds, 0 for immediate)
    iteration_delay: 0

  single_shot:
    # Whether to retry failed tasks in single-shot mode
    retry_on_failure: false

checkpoints:
  # Enable automatic checkpointing
  enabled: true

  # Always checkpoint at wave boundaries
  at_wave_boundary: true

  # Optional: checkpoint after each task (more granular but slower)
  on_task_complete: false

hooks:
  # Enable hook execution
  enabled: true

  # Hooks run at different lifecycle points
  pre_wave_start:
    - checkpoint_state

  post_task_complete:
    - log_event
    - update_state

  on_failure:
    - log_failure
    - check_retry

  on_session_end:
    - final_checkpoint

# Failure handling configuration (Phase 7)
failure:
  default_strategy: retry
  max_retries: 3
  cascade_policy: block_dependents
```

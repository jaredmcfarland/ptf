**Structure (follow /ptf:plan command pattern):**

1. **Frontmatter:**
   - name: ptf:execute
   - description: Execute single wave or next pending wave
   - allowed-tools: Read, Write, Bash, Glob, Grep, Task

2. **Objective section:**
   - Usage: `/ptf:execute` (next wave) or `/ptf:execute 2` (wave 2)
   - Requires: graph.yaml (waves computed), execution.yaml (initialized)
   - After: Run again for next wave or /ptf:execute-all

3. **Process section with phases:**

   Phase 1: Load State
   - Check prerequisites exist (.orchestrator/state/execution.yaml)
   - Read current_wave and status from execution.yaml
   - Handle terminal states (completed, failed)
   - Determine target wave (argument or current_wave)

   Phase 2: Validate Wave Ready
   - Check wave dependencies satisfied (prior waves completed)
   - Verify tasks exist for target wave in graph.yaml
   - Return error if wave not ready

   Phase 3: Dispatch Orchestrator
   - Spawn ptf-orchestrator via Task tool with:
     - Target wave number
     - Mode: single-wave
   - Wait for orchestrator completion

   Phase 4: Handle Results
   - Parse orchestrator return (WAVE COMPLETE, etc.)
   - Display wave summary with task results
   - Show next steps based on outcome:
     - Success: Run /ptf:execute for next wave
     - Partial: Show failures, offer /ptf:retry
     - Failed: Show blockers, offer recovery options

4. **Success criteria checklist:**
   - Target wave identified
   - Wave dependencies validated
   - Orchestrator dispatched successfully
   - Results displayed with next steps

Follow pattern from /ptf:plan command for structure.

Create the hook files for execution lifecycle events.

**Requirements to implement:**
- HOOK-01: post-task-complete hook
- HOOK-02: pre-wave-start hook
- HOOK-03: on-failure hook
- HOOK-04: on-session-end hook

First, create the hooks directory:
```bash
mkdir -p .claude/hooks/ptf
```

**Hook file structure (each file):**

```markdown
---
name: {hook-name}
description: {what triggers this hook}
trigger: {lifecycle point}
---

<when>
{Description of when this hook fires}
</when>

<actions>
{Default actions this hook performs}
- action 1
- action 2
</actions>

<context_available>
{What data is available to the hook}
- task_id: The task that triggered (if applicable)
- wave: The current wave number
- result: The task/wave result (if applicable)
</context_available>

<customization>
{How users can customize this hook}
Edit this file to add custom actions.
</customization>
```

**Specific hooks:**

1. **post-task-complete.md** (HOOK-01)
   - Trigger: After each task completes (success or failure)
   - Default actions: log_event, update_state, register_artifacts
   - Context: task_id, result (success/failure), outputs

2. **pre-wave-start.md** (HOOK-02)
   - Trigger: Before first task in wave dispatched
   - Default actions: checkpoint_state, validate_dependencies
   - Context: wave_number, tasks_in_wave

3. **on-failure.md** (HOOK-03)
   - Trigger: When task fails after all retries exhausted
   - Default actions: log_failure, check_cascade_policy, update_failure_record
   - Context: task_id, error, attempts, cascade_targets

4. **on-session-end.md** (HOOK-04)
   - Trigger: Execution ends (complete, abort, or interrupt)
   - Default actions: final_checkpoint, cleanup_temp_files, summary_report
   - Context: end_reason (complete/abort/interrupt), session_stats

Hooks are documentation files that describe the hook interface.
Actual hook execution is handled by the orchestrator which reads these.

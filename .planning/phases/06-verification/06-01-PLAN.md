**Structure (follow ptf-executor.md pattern):**

1. **Frontmatter:**
   ```yaml
   ---
   name: ptf-verifier
   description: Independently verifies task outputs against verification criteria
   tools: Read, Bash, Glob, Grep
   ---
   ```

2. **Role section:**
   - You are the PTF verification specialist
   - Spawned by orchestrator AFTER executor claims VERIFICATION PASSED
   - Receive: task ID, verification criteria, expected outputs
   - Job: Run all verification checks, return pass/fail with details
   - Critical: Independent from executor - don't trust claims, verify by checking

3. **Philosophy section:**
   - Trust But Verify: Executor claims completion, verifier confirms it
   - Independent Judgment: Fresh context means no bias from execution
   - Multi-Modal Verification: Multiple check types for comprehensive validation
   - Fail-Fast Order: exists -> syntax -> contains -> runs -> custom

4. **Verification Types (implementation section):**
   For each type, provide:
   - Description and when to use
   - Exact bash implementation
   - Expected output format

   ```
   exists:
     [ -f "$target" ] or [ -d "$target" ]
     Returns: "File exists at path" or "NOT FOUND"

   contains:
     grep -q "$expected" "$target"
     Returns: "Pattern found" or "Pattern not found"

   runs:
     eval "$target" 2>&1
     actual_exit=$?
     Returns: "Command exited N" vs expected (default 0)

   syntax:
     Based on file extension:
     - .ts/.tsx: npx tsc --noEmit "$target"
     - .py: python -m py_compile "$target"
     - .json: jq . "$target" > /dev/null
     - .yaml/.yml: yq . "$target" > /dev/null
     - .sql: Return true (no universal SQL validator)
     Returns: "Syntax valid" or "Syntax errors"

   custom:
     eval "$target" 2>&1
     Returns: "Custom check passed/failed"
   ```

5. **Execution Flow (steps):**
   - load_criteria: Read task from .orchestrator/decomposition/tasks/{task-id}.yaml
   - verify_outputs_exist: Check each output in task.outputs exists
   - run_verification_steps: Execute each step in task.verify array
   - compile_results: Aggregate results, determine overall pass/fail
   - return_results: Output structured verification result

6. **Structured Returns section:**
   Two return formats:

   VERIFICATION PASSED:
   ```markdown
   ## VERIFICATION PASSED

   **Task:** {task_id}
   **Checks:** {N}/{N} passed

   ### Results

   | Type | Target | Status | Message |
   |------|--------|--------|---------|
   | exists | path/to/file | PASS | File exists |
   | contains | pattern | PASS | Pattern found |

   ### Artifact Checksums

   | Path | Checksum |
   |------|----------|
   | output.ts | sha256:{first-8}... |
   ```

   VERIFICATION FAILED:
   ```markdown
   ## VERIFICATION FAILED

   **Task:** {task_id}
   **Checks:** {M}/{N} passed

   ### Failures

   | Type | Target | Expected | Actual |
   |------|--------|----------|--------|
   | contains | pattern | Found | NOT FOUND |

   ### Passed Checks

   | Type | Target | Message |
   |------|--------|---------|
   | exists | path | File exists |
   ```

7. **Edge Cases section:**
   - Missing task file: Return error, cannot verify
   - Empty verify array: Pass by default (no checks = no failures)
   - Timeout handling: Default 60s per check, configurable
   - Syntax check for unknown extension: Skip with warning

8. **Anti-patterns section:**
   - Don't trust executor's verification claims
   - Don't skip checks because "it looks fine"
   - Don't modify any files (read-only verification)
   - Don't assume output type from extension alone

<verification_strategies>

## Adapter-Driven Verification

When verifying, check if domain adapter provides verification_strategies for the artifact type.

**Process:**

1. Load adapter from .orchestrator/config.yaml -> domain_adapter
2. Read adapter file from adapters/{adapter}.yaml
3. Look up artifact type's verification_strategies
4. Apply adapter strategies in addition to task-declared verification

**Example from software-development adapter:**

```yaml
verification_strategies:
  source-code:
    - method: exists
    - method: syntax
    - method: runs
      command_template: "npx tsc --noEmit {path}"

  migration:
    - method: exists
    - method: syntax
    - method: runs
      command_template: "npx prisma validate"

  test:
    - method: exists
    - method: runs
      command_template: "npm test -- {path}"
```

**Strategy priority:**
1. Task-declared verification (explicit in task.verify)
2. Adapter strategies for artifact type (if available)
3. Default: exists check only

**Integration:**

```
get_verification_steps(task):
  # Start with task's explicit verification
  steps = task.verify or []

  # Add adapter strategies if available
  adapter = load_adapter()
  for output in task.outputs:
    artifact_type = output.type
    if adapter.verification_strategies[artifact_type]:
      for strategy in adapter.verification_strategies[artifact_type]:
        # Don't duplicate existing checks
        if not already_in_steps(strategy.method, steps):
          steps.append(strategy)

  return steps
```

**Fallback when no adapter:**
- Default to exists check for all outputs
- Log that adapter strategies are not available

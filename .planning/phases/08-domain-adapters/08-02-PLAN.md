## Domain Adapters

Adapters customize PTF for specific domains. Located in `adapters/`:
- `software-development.yaml` - Code, tests, configs, deployments
- `research.yaml` - Literature review, experiments, analysis, writing
- `template.yaml` - Base for custom adapters

### Adapter Sections

| Section | Purpose | Used By |
|---------|---------|---------|
| `questioning` | Init clarification questions | `/ptf:init` |
| `decomposition` | Heuristics and atomicity criteria | `ptf-decomposer` |
| `constitution` | Project principles template | `/ptf:init` |
| `artifacts` | Types and verification strategies | `ptf-verifier` |
| `dependencies` | Inference patterns | `ptf-dependency-analyzer` |

### Questioning Section

Drives the `/ptf:init` clarification process:

```yaml
questioning:
  init_questions:
    - category: core_value        # Grouping for the question
      question: "What's the ONE thing...?"  # Actual question
      why: "Identifies critical path"       # Why it matters
      options_template:                     # Example answers
        - "The {main_feature}"
```

### Decomposition Section

Controls how goals break into tasks:

```yaml
decomposition:
  subgoal_heuristics:
    - name: by-layer              # Heuristic identifier
      description: "Split by architectural layer"
      when_to_use: "Feature spans multiple layers"

  atomicity_criteria:
    - criterion: single-file      # What to check
      check: "Task produces at most one file"
      fail_signal: "outputs array has >3 files"

  max_recursion_depth: 5
```

### Artifacts Section

Defines output types and how to verify them:

```yaml
artifacts:
  types:
    - name: source-code
      extensions: [.ts, .js, .py]

  verification_strategies:
    source-code:
      - method: exists
      - method: syntax
      - method: runs
        command_template: "npx tsc --noEmit {path}"
```

### Dependencies Section

Enables automatic dependency inference:

```yaml
dependencies:
  common_patterns:
    - name: schema-to-repository
      from_type: migration
      to_type: source-code
      confidence: high

  inference_hints:
    - pattern: "import.*from"
      implies: depends on imported module
```

### Creating Custom Adapters

1. Copy `adapters/template.yaml` to `adapters/{your-domain}.yaml`
2. Replace all `[CUSTOMIZE]` markers with domain-specific content
3. Test with `/ptf:init --domain={your-domain}`
4. Validate against `schemas/adapter.schema.yaml`

**Minimum requirements for a valid adapter:**
- All 5 sections present (questioning, decomposition, constitution, artifacts, dependencies)
- At least 3 init_questions
- At least 2 subgoal_heuristics
- At least 3 atomicity_criteria
- At least 2 artifact types with verification strategies
- At least 2 dependency patterns

### Adapter Integration Points

| Phase | How Adapter Is Used |
|-------|---------------------|
| `/ptf:init` | Loads questioning section, asks init_questions |
| `/ptf:decompose` | Applies subgoal_heuristics, checks atomicity_criteria |
| `/ptf:plan` | Uses dependency patterns for inference |
| `/ptf:verify` | Applies verification_strategies by artifact type |
| Constitution | Generated from constitution.template during init |
```

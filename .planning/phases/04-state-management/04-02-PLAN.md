Create the event log schema based on 04-RESEARCH.md "Pattern 1: Event Sourcing for History".

**Event Log Schema (schemas/event-log.schema.yaml):**

```yaml
$schema: "http://json-schema.org/draft-07/schema#"
$id: "https://ptf.dev/schemas/event-log.schema.yaml"
title: EventLogEntry
description: Single event in the append-only JSONL event log (.orchestrator/history/events.jsonl)
type: object
required:
  - ts
  - event
properties:
  ts:
    type: string
    format: date-time
    description: ISO 8601 timestamp when event occurred
  event:
    type: string
    enum:
      # Session events
      - session_started
      - session_resumed
      - session_paused
      - session_completed
      - session_failed
      # Wave events
      - wave_started
      - wave_completed
      - wave_failed
      # Task events
      - task_started
      - task_completed
      - task_failed
      - task_skipped
      - task_retry
      # Artifact events
      - artifact_produced
      - artifact_verified
      - artifact_validation_failed
      # Checkpoint events
      - checkpoint_started
      - checkpoint_completed
      # System events
      - goal_received
      - plan_generated
      - error
    description: Event type
  # Context fields (vary by event type)
  session:
    type: string
    description: Session ID (session events)
  wave:
    type: integer
    description: Wave number (wave/task events)
  task:
    type: string
    description: Task ID (task events)
  attempt:
    type: integer
    description: Attempt number (task_retry, task_failed)
  duration_s:
    type: number
    description: Duration in seconds (completed events)
  path:
    type: string
    description: File path (artifact events)
  checksum:
    type: string
    description: SHA-256 checksum (artifact events)
  reason:
    type: string
    description: Explanation (failures, skips)
  goal_hash:
    type: string
    description: Hash of goal content (goal_received)
  error:
    type: string
    description: Error message (error events)
  outputs:
    type: array
    items:
      type: string
    description: Output paths (task_completed)
```

The schema describes single lines in the JSONL file. Each line is valid JSON matching this schema.

**Key properties documented in description:**
- Append-only: Never modify existing lines
- Line-level atomicity: Each line is a complete event
- Replayable: Can reconstruct state from events
- Greppable: Easy to filter with grep/jq

Create the state manager subagent that handles checkpoints and event logging.

**Required frontmatter:**
```yaml
---
name: ptf-state-manager
description: Manages execution state, checkpoints, and event logging for PTF
tools: Read, Write, Bash, Glob
---
```

**Required sections:**

1. **&lt;role&gt;**
   - You are the PTF state manager
   - Responsible for: state persistence, checkpoints, event logging, artifact tracking
   - Job: Ensure execution state survives interruptions

2. **&lt;philosophy&gt;**
   Three core principles from 04-RESEARCH.md:
   - Event Sourcing: All changes recorded as timestamped events
   - Atomic Checkpoints: Write details before summary, execution.yaml last
   - Idempotent Operations: Safe to re-run (full state writes, not deltas)

3. **&lt;state_structure&gt;**
   Document the .orchestrator/state/ directory structure:
   ```
   .orchestrator/
   ├── state/
   │   ├── execution.yaml          # Master state (SOURCE OF TRUTH)
   │   ├── waves/
   │   │   └── wave-{N}.yaml       # Per-wave state
   │   └── tasks/
   │       └── {task-id}.yaml      # Per-task state
   ├── artifacts/
   │   └── manifest.yaml           # Artifact registry
   └── history/
       └── events.jsonl            # Append-only event log
   ```

4. **&lt;execution_flow&gt;** with operations:

   **operation name="init_state"**
   - Create state directory structure if not exists
   - Initialize execution.yaml with status: pending
   - Create empty manifest.yaml
   - Create events.jsonl with goal_received event
   - Input: plan from graph.yaml
   - Output: initialized state files

   **operation name="start_wave"**
   - Update execution.yaml: current_wave, status: running
   - Create wave-{N}.yaml with status: running
   - Mark wave tasks as ready in task state files
   - Append wave_started event
   - Input: wave number
   - Output: updated state files

   **operation name="task_started"**
   - Update task state: status: running, attempt info
   - Append task_started event
   - Input: task_id, attempt number
   - Output: updated task state

   **operation name="task_completed"**
   - Update task state: status: completed, outputs_produced
   - Register artifacts in manifest.yaml with checksums
   - Append task_completed and artifact_produced events
   - Input: task_id, outputs array
   - Output: updated task and manifest

   **operation name="task_failed"**
   - Update task state: status: failed, error message
   - Append task_failed event
   - Check retry policy: if attempts < max, keep task runnable
   - Input: task_id, error, attempt
   - Output: updated task state

   **operation name="checkpoint_wave"**
   Critical: follows specific write order for atomicity.

   ```markdown
   **Checkpoint Protocol (from 04-RESEARCH.md):**

   1. Write all task state files (details first)
      For each task in wave:
      - Write .orchestrator/state/tasks/{task-id}.yaml

   2. Write wave state file
      - Write .orchestrator/state/waves/wave-{N}.yaml

   3. Update artifact manifest
      - For completed tasks, register outputs in manifest.yaml

   4. Append events to log
      - Append checkpoint_started
      - Append wave_completed
      - Append checkpoint_completed

   5. Update execution.yaml LAST (commit marker)
      - Update wave_summary[N]: completed
      - Update current_wave: N+1 (or keep if last)
      - Update progress counters
      - Update session.last_update

   **Why this order matters:**
   - If interrupted before step 5: Resume will re-checkpoint (idempotent)
   - If interrupted after step 5: State is consistent
   - execution.yaml is the "commit" that marks checkpoint complete
   ```

   **operation name="validate_artifacts"**
   For resume: verify artifacts exist and have correct checksums.

   ```markdown
   For each artifact in manifest.yaml:
   1. Check file exists at path
   2. Compute SHA-256: shasum -a 256 {path} | cut -d' ' -f1
   3. Compare with stored checksum
   4. If mismatch: mark task for re-execution
   5. Return validation results
   ```

5. **&lt;event_logging&gt;**
   How to write events:

   ```bash
   # Append single event (atomic at filesystem level)
   echo '{"ts":"'$(date -u +%Y-%m-%dT%H:%M:%SZ)'","event":"task_completed","task":"auth-schema","duration_s":179}' >> .orchestrator/history/events.jsonl
   ```

   - Each event is single JSON line
   - Timestamp is ISO 8601 UTC
   - Never edit existing events
   - Include relevant context (task, wave, duration, outputs)

6. **&lt;structured_returns&gt;**
   - STATE INITIALIZED: file counts, ready status
   - CHECKPOINT COMPLETE: wave number, tasks checkpointed, duration
   - VALIDATION RESULTS: artifacts checked, valid count, invalid list
   - STATE ERROR: operation, error message, recovery suggestion
